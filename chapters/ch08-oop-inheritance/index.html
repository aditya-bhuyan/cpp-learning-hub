Chapter 08 — OOP: Inheritance & Polymorphism

Build class hierarchies, override behavior at run time, and program against abstract interfaces.

📖 Learning 💻 Examples ✏️ Exercises ✅ Solutions 🧠 Quiz

8.1 Inheritance — the "is-a" Relationship

Inheritance lets you define a new class by building on an existing one. The existing class is called the base class (also parent or superclass); the new class is the derived class (child or subclass). The derived class automatically receives the data members and member functions of the base class and may add new ones or change inherited behavior.

Use public inheritance only when the relationship can be read as "is-a": a Dog is an Animal; a Circle is a Shape. If the natural reading is "has-a" (a Car has an Engine), use composition — make the engine a data member instead.

Why inheritance? It gives you code reuse (common code lives once in the base class) and polymorphism (code written against the base class works with every derived class — covered from section 8.6 on).

8.2 Single Inheritance Syntax

The base class is named after a colon, together with an access specifier:

class Animal {
public:
    string name;
    void eat() const { cout << name << " is eating\n"; }
};

class Dog : public Animal {          // Dog is-a Animal
public:
    void bark() const { cout << name << " says Woof!\n"; }
};

int main() {
    Dog d;
    d.name = "Rex";    // inherited data member
    d.eat();           // inherited member function
    d.bark();          // Dog's own member function
    return 0;
}

Dog contains everything in Animal plus its own members. A derived object is stored as the base-class part first, followed by the members added by the derived class.

Kinds of inheritance

The access specifier before the base class name caps how the inherited members appear in the derived class:

Base member is…public inheritanceprotected inheritanceprivate inheritance
publicpublicprotectedprivate
protectedprotectedprotectedprivate
privatenever accessible in the derived class (it exists, but is hidden)
Rule of thumb Almost always write class Derived : public Base. Private and protected inheritance model "implemented-in-terms-of", not "is-a", and you cannot convert a Derived* to a Base* outside the class. Also note: for class the default inheritance is private; for struct it is public. Always state it explicitly.

8.3 Protected Members

There are three access levels, and inheritance adds a new meaning to the middle one:

SpecifierSame classDerived classOutside code
publicYesYesYes
protectedYesYesNo
privateYesNoNo
 
class Account {
private:
    int pin = 1234;          // only Account can touch this
protected:
    double balance = 0.0;    // Account and derived classes can touch this
public:
    void deposit(double amt) { balance += amt; }
};

class SavingsAccount : public Account {
public:
    void addInterest(double rate) {
        balance += balance * rate;   // OK: protected, accessible in derived class
        // pin = 0;                  // ERROR: private in Account
    }
};

int main() {
    SavingsAccount s;
    s.deposit(100);
    // s.balance = 5;                // ERROR: protected, not accessible outside
    return 0;
}
Protected data weakens encapsulation Every derived class can now read and modify balance, so a change to the base class can break any of them. Prefer private data plus protected accessor functions when you can.

8.4 Constructors and Destructors in a Hierarchy

A derived object contains a base-class sub-object, and that sub-object must be built first. Constructors are not inherited, so the derived constructor must tell the compiler which base constructor to run. Do that in the member-initializer list: 

class Person {
protected:
    string name;
    int    age;
public:
    Person(const string& n, int a) : name(n), age(a) {
        cout << "Person ctor\n";
    }
    ~Person() { cout << "Person dtor\n"; }
};

class Student : public Person {
    string school;
public:
    //          pass arguments up to the base constructor
    Student(const string& n, int a, const string& s)
        : Person(n, a), school(s) {            // Derived(args) : Base(args) { }
        cout << "Student ctor\n";
    }
    ~Student() { cout << "Student dtor\n"; }
};

int main() {
    Student s("Ana", 20, "MIT");
    return 0;
}
Person ctor
Student ctor
Student dtor
Person dtor
EventOrder
ConstructionBase → members → Derived body (base first)
DestructionDerived body → members → Base (exact reverse)
No default base constructor? If the base class has no default constructor and you do not call one explicitly in the initializer list, the program will not compile. If you omit the call and a default constructor exists, it is used silently.

8.5 Overriding vs Overloading — Different Concepts!

Beginners often mix these two up. They share the idea "same function name, different behavior", but they work in completely different ways.

OverloadingOverriding
WhereSame scope (usually one class)Base class and derived class
SignatureMust differ (parameter types/count)Must be identical (and const-ness)
ResolvedAt compile time (static)At run time, if the base function is virtual
PurposeConvenient variants of one operationSpecialize inherited behavior
virtual needed?NoYes, for run-time dispatch
 
class Printer {
public:
    // OVERLOADING: same name, different parameter lists, same class
    void print(int x)           const { cout << "int: "    << x << "\n"; }
    void print(const string& s) const { cout << "string: " << s << "\n"; }

    virtual void hello() const { cout << "Hello from Printer\n"; }
    virtual ~Printer() = default;
};

class FancyPrinter : public Printer {
public:
    // OVERRIDING: same signature as the base virtual function
    void hello() const override { cout << "Hello from FancyPrinter\n"; }
};
Name hiding If a derived class declares any function called print, it hides all base-class overloads named print — even ones with different parameters. Bring them back with using Base::print; inside the derived class.

8.6 The virtual Keyword — Runtime Polymorphism

Polymorphism means "many forms": the same call can run different code depending on the actual type of the object. Without virtual, C++ chooses the function at compile time from the static type of the expression (static binding). Marking a member function virtual makes the choice at run time from the real type of the object (dynamic binding). 

class Animal {
public:
    void eat() const           { cout << "Animal eats\n"; }      // NOT virtual
    virtual void sound() const { cout << "Some sound\n"; }       // virtual
    virtual ~Animal() = default;
};

class Dog : public Animal {
public:
    void eat() const           { cout << "Dog eats\n"; }        // hides, does not override
    void sound() const override { cout << "Woof\n"; }           // overrides
};

int main() {
    Dog d;
    Animal* p = &d;      // base pointer to derived object

    p->eat();            // "Animal eats"  — static binding, decided by pointer type
    p->sound();          // "Woof"         — dynamic binding, decided by object type
    return 0;
}

Once a function is virtual in the base class, every function in derived classes with the same signature is automatically virtual too (even without repeating the keyword).

How it works (briefly) Compilers typically implement this with a vtable: each class with virtual functions has a hidden table of function pointers, and each object carries a hidden pointer (the vptr) to its class's table. A virtual call follows that pointer. The cost is one extra pointer per object and one indirection per call.

8.7 Polymorphism via Base Pointers and References

A pointer or reference to a base class may refer to any object derived from it. Dynamic binding applies only when you call through a pointer or reference — that is where polymorphic code lives. 

void makeNoise(const Animal& a) {   // accepts Animal, Dog, Cat, ...
    a.sound();                       // dispatches to the real type at run time
}

int main() {
    Dog d;
    Cat c;

    makeNoise(d);                    // Woof
    makeNoise(c);                    // Meow

    vector<Animal*> zoo = { &d, &c };
    for (const Animal* a : zoo) a->sound();   // Woof, Meow
    return 0;
}

The function makeNoise was written once and works for animal types that do not even exist yet. That is the main payoff: program against the base-class interface, not the concrete types.

8.8 Pure Virtual Functions

Sometimes a base-class function cannot have a sensible implementation — what is the area of a generic "shape"? Declare it pure virtual with = 0: 

class Shape {
public:
    virtual void   draw() const = 0;   // pure virtual: no implementation required
    virtual double area() const = 0;
    virtual ~Shape() = default;
};

A pure virtual function says: "every concrete derived class must provide this." Any class with at least one pure virtual function becomes an abstract class.

8.9 Abstract Classes

  • An abstract class cannot be instantiated: Shape s; and new Shape are errors.
  • You can have pointers and references to it — that is how polymorphism is used.
  • A derived class that does not override all inherited pure virtuals is itself abstract.
  • It can still have data members, constructors, and ordinary member functions.
  • It defines an interface contract: callers depend on the contract, implementers fulfil it.
class Circle : public Shape {
    double r;
public:
    explicit Circle(double radius) : r(radius) {}
    void   draw() const override { cout << "Drawing circle\n"; }
    double area() const override { return 3.14159265 * r * r; }
};

int main() {
    // Shape s;                 // ERROR: Shape is abstract
    Circle c(2.0);              // OK: Circle overrides every pure virtual
    Shape& ref = c;             // OK: reference to the abstract base
    ref.draw();
    return 0;
}
Interfaces in C++ C++ has no interface keyword. By convention, an interface is an abstract class containing only pure virtual functions and a virtual destructor.

8.10 The override Keyword (C++11)

Overriding fails silently if the signature differs by even a tiny detail — you accidentally create a brand-new function instead. override makes the compiler check your intent: 

class Base {
public:
    virtual void show() const { cout << "Base\n"; }
    virtual void set(int x)   { }
    virtual ~Base() = default;
};

class Derived : public Base {
public:
    void show()        { cout << "Derived\n"; }        // forgot const: NOT an override! (silent bug)
    void set(long x)   { }                             // int vs long:  NOT an override! (silent bug)
};

class DerivedFixed : public Base {
public:
    void show() const override { cout << "Derived\n"; }  // OK
    // void set(long x) override { }                     // ERROR: does not override anything
    void set(int x)  override { }                        // OK
};
Habit Put override on every function that is meant to override. If someone later changes the base signature, all affected derived classes immediately fail to compile instead of misbehaving.

8.11 The final Keyword

final (C++11) closes a door in two places:

// 1. final on a function: derived classes may not override it any further
class Base {
public:
    virtual void run() { }
    virtual ~Base() = default;
};

class Mid : public Base {
public:
    void run() override final { }      // last allowed override
};

class Leaf : public Mid {
public:
    // void run() override { }         // ERROR: Mid::run is final
};

// 2. final on a class: nobody may derive from it
class Sealed final : public Base { };

// class Bad : public Sealed { };      // ERROR: Sealed is final

Use final to document design intent and to let the compiler optimize (it can bind calls directly when it knows no further override can exist).

8.12 Virtual Destructors

This is one of the most important rules in C++ OOP: if a class is meant to be used polymorphically (has virtual functions), give it a virtual destructor. 

class Base {
public:
    ~Base() { cout << "~Base\n"; }               // NOT virtual — dangerous!
};

class Derived : public Base {
    int* data = new int[1000];
public:
    ~Derived() { delete[] data; cout << "~Derived\n"; }
};

int main() {
    Base* p = new Derived;
    delete p;      // UNDEFINED BEHAVIOR: only ~Base runs, ~Derived is skipped
                   // → data is never freed → memory leak
    return 0;
}

The fix is a single keyword:

class Base {
public:
    virtual ~Base() { cout << "~Base\n"; }       // now delete via Base* is safe
};
// delete p;   →   ~Derived   then   ~Base

With a virtual destructor, delete p looks up the real type of the object, runs ~Derived() first and then ~Base(). If the base needs no cleanup, write virtual ~Base() = default;.

Deleting a derived object through a non-virtual-destructor base pointer is undefined behavior Typical symptoms are leaked resources and partially destroyed objects. The compiler may warn (-Wnon-virtual-dtor, -Wdelete-non-virtual-dtor) — enable those warnings.

8.13 Multiple Inheritance

C++ allows a class to have more than one base class. Separate the bases with commas:

class Flyer {
public:
    void fly() const { cout << "Flying\n"; }
};

class Swimmer {
public:
    void swim() const { cout << "Swimming\n"; }
};

class Duck : public Flyer, public Swimmer {     // Duck has both abilities
public:
    void quack() const { cout << "Quack\n"; }
};

int main() {
    Duck d;
    d.fly();
    d.swim();
    d.quack();
    return 0;
}

Base constructors run in the order the bases are listed in the class declaration (not the order in the initializer list). Multiple inheritance is also commonly used to implement several interfaces (abstract classes) at once, which is generally safe and idiomatic.

Ambiguity

If both bases define a member with the same name, an unqualified use is ambiguous:

struct A { void hello() { cout << "A\n"; } };
struct B { void hello() { cout << "B\n"; } };
struct C : A, B { };

int main() {
    C c;
    // c.hello();      // ERROR: ambiguous — A::hello or B::hello?
    c.A::hello();      // OK: resolve with the scope operator
    c.B::hello();
    return 0;
}

The Diamond Problem

Trouble starts when two bases share a common ancestor, forming a diamond: 

        Animal
        /    \
     Fish    Bird
        \    /
      FlyingFish
class Animal { public: int age = 0; };
class Fish : public Animal { };
class Bird : public Animal { };
class FlyingFish : public Fish, public Bird { };

int main() {
    FlyingFish f;
    // f.age = 3;        // ERROR: ambiguous — Fish::Animal::age or Bird::Animal::age?
    f.Fish::age = 3;     // there are TWO separate Animal sub-objects inside FlyingFish
    f.Bird::age = 5;
    return 0;
}

FlyingFish contains two Animal sub-objects — one through each path — which wastes memory and produces ambiguity.

Virtual Base Classes — the Fix

Declare the shared base as virtual in the intermediate classes. Now all paths share a single Animal sub-object: 

class Animal { public: int age = 0; };
class Fish : virtual public Animal { };
class Bird : virtual public Animal { };
class FlyingFish : public Fish, public Bird { };

int main() {
    FlyingFish f;
    f.age = 3;           // OK: only one Animal::age exists
    return 0;
}
Who constructs a virtual base? The most derived class (here FlyingFish) is responsible for initializing the virtual base directly: FlyingFish(...) : Animal(...), Fish(...), Bird(...) { }. The Animal initializers inside Fish and Bird are ignored in that case. Virtual inheritance adds some size and access overhead, so use it only where a real diamond exists.

8.14 Runtime Type Information (RTTI) — a Brief Intro

Sometimes you hold a Base* and must find out what the object really is. RTTI offers two tools. Both require the base class to be polymorphic (have at least one virtual function).

dynamic_cast

A checked downcast. For pointers it returns nullptr if the object is not of the requested type; for references it throws std::bad_cast. 

#include <iostream>
#include <typeinfo>
using namespace std;

class Animal { public: virtual ~Animal() = default; };
class Dog : public Animal { public: void fetch() const { cout << "Fetching!\n"; } };
class Cat : public Animal { };

void test(Animal* a) {
    if (Dog* d = dynamic_cast<Dog*>(a)) {      // succeeds only if *a is really a Dog
        d->fetch();
    } else {
        cout << "Not a dog\n";
    }
}

int main() {
    Dog dog;  Cat cat;
    test(&dog);      // Fetching!
    test(&cat);      // Not a dog
    return 0;
}

typeid

Returns a std::type_info object describing the type; compare with == or print .name().

Animal* a = new Dog;

cout << typeid(*a).name() << "\n";          // implementation-defined, e.g. "3Dog" or "class Dog"
cout << (typeid(*a) == typeid(Dog)) << "\n"; // 1  — dynamic type is exactly Dog
cout << (typeid(*a) == typeid(Animal)) << "\n"; // 0
delete a;
Use RTTI sparingly Frequent dynamic_cast usage is often a design smell: if you keep asking "what type is this?", the question probably belongs in a virtual function. Also remember that typeid(...).name() is not portable text.

8.15 Object Slicing

Polymorphism works through pointers and references. If you copy a derived object into a base object by value, the derived part is cut off — object slicing. 

class Animal {
public:
    virtual void sound() const { cout << "Some sound\n"; }
    virtual ~Animal() = default;
};

class Dog : public Animal {
    string breed = "Labrador";           // extra data only Dog has
public:
    void sound() const override { cout << "Woof (" << breed << ")\n"; }
};

void byValue(Animal a)      { a.sound(); }    // copy → sliced!
void byRef(const Animal& a) { a.sound(); }    // no copy → polymorphic

int main() {
    Dog d;

    Animal a = d;            // slicing: only the Animal part is copied
    a.sound();               // "Some sound"  — it is a plain Animal now

    byValue(d);              // "Some sound"
    byRef(d);                // "Woof (Labrador)"

    vector<Animal> bad;     // stores Animal objects: every Dog pushed in is sliced
    bad.push_back(d);
    bad[0].sound();          // "Some sound"
    return 0;
}
The slicing trap Slicing silently discards the derived data members and the derived behavior (the vptr is reset to the base class's table). It compiles without errors. To avoid it: pass polymorphic objects by reference or pointer, store vector<Base*> or vector<unique_ptr<Base>> in containers, and consider deleting the base copy constructor in abstract bases.

8.16 Key Takeaways

  • Inheritance models an is-a relationship: class Dog : public Animal. For "has-a", use composition.
  • protected members are visible to derived classes but not to outside code; private members are not visible to derived classes.
  • Derived constructors call the base constructor via the initializer list: Derived(args) : Base(args) { }. Construction goes base→derived; destruction goes derived→base.
  • Overloading = same name, different parameters, compile-time. Overriding = same signature in a derived class, run-time (with virtual).
  • virtual enables dynamic binding; it works only through pointers and references.
  • virtual void f() = 0; makes a function pure virtual and the class abstract (cannot be instantiated; defines an interface).
  • Always write override on overriding functions; use final to stop further overriding or inheriting.
  • A base class with virtual functions needs a virtual destructor, or delete via a base pointer is undefined behavior.
  • Multiple inheritance can cause ambiguity and the diamond problem; solve it with virtual base classes.
  • dynamic_cast and typeid (RTTI) work on polymorphic types; use them sparingly.
  • Object slicing happens when a derived object is copied into a base object by value — use references, pointers, or smart pointers instead.
