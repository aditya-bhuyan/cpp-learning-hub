Chapter 13 — Exception Handling

Robust error handling with try/catch/throw, the standard exception hierarchy, RAII, and exception safety guarantees.

📖 Learning 💻 Examples ✏️ Exercises ✅ Solutions 🧠 Quiz

13.1 Why Exceptions? Error Codes vs Exceptions

When a function encounters a condition it cannot handle itself — a file that doesn't exist, a buffer overflow, an invalid argument — it must communicate failure to its caller. Two dominant strategies exist in C++: error codes and exceptions.

AspectError CodesExceptions
Return pathNormal return valueSeparate exceptional path
Forced handlingNo — caller can silently ignoreYes — uncaught exception calls std::terminate
Code clarityCluttered with checks at every callHappy path is clean; error handling is separated
PerformanceZero overhead on non-error pathSmall overhead on throw (zero-cost on non-throw with modern ABI)
Constructor errorsConstructors have no return value — awkwardThrow from constructor is natural and safe
Deep call chainsEvery frame must propagate the codeException propagates automatically — no boilerplate

Guideline: Prefer exceptions for truly exceptional conditions (events that should not occur in correct usage). Use error codes or std::expected (C++23) for expected, frequent, or performance-critical failure paths.

13.2 try / catch / throw Syntax

Three keywords form the core mechanism:

  • throw expr — raises an exception object and begins stack unwinding.
  • try { … } — marks a block whose exceptions you want to handle.
  • catch (Type& e) { … } — handles a specific exception type.
#include <iostream>
#include <stdexcept>
using namespace std;

double divide(double a, double b) {
    if (b == 0.0)
        throw invalid_argument("Division by zero");   // throw an exception
    return a / b;
}

int main() {
    try {
        cout << divide(10, 2) << "\n";   // OK: prints 5
        cout << divide(10, 0) << "\n";   // throws!
    }
    catch (const invalid_argument& e) {
        cerr << "Caught: " << e.what() << "\n";
    }
    return 0;
}

13.3 Throwing by Value, Catching by Reference

Always throw by value: the exception object is copied/moved into a special exception storage area. Always catch by const reference: this avoids an extra copy, preserves the original dynamic type (important for polymorphism), and prevents accidental modification. 

// Correct idiom
throw MyException("message");          // throw by value (temporary)

catch (const MyException& e) { … }    // catch by const reference — best practice
catch (MyException e)         { … }    // BAD: copies the object, loses derived type
catch (MyException* e)        { … }    // BAD: who deletes the pointer?
Rule of Thumb Throw by value. Catch by const reference. Never catch by pointer unless you threw a pointer (which you should not do in modern C++).

13.4 Catch-All: catch(...)

A catch(...) clause catches any exception regardless of type. It is typically used as a last-resort handler to log an unexpected failure or perform cleanup before rethrowing. 

try {
    riskyOperation();
}
catch (const std::exception& e) {
    cerr << "Standard exception: " << e.what() << "\n";
}
catch (...) {
    // Catches int, char*, and any other non-std::exception throw
    cerr << "Unknown exception caught!\n";
    throw;   // rethrow so the caller (or terminate) still sees it
}

13.5 Standard Exception Hierarchy

All standard exceptions in <stdexcept> and <exception> derive from std::exception:

ClassHeaderTypical use
std::exception<exception>Base class; provides what()
std::logic_error<stdexcept>Errors detectable before runtime (preconditions)
std::invalid_argument<stdexcept>Bad argument passed to a function
std::out_of_range<stdexcept>Index or value out of valid range
std::length_error<stdexcept>Container size exceeds maximum
std::runtime_error<stdexcept>Errors detectable only at runtime
std::range_error<stdexcept>Result outside representable range
std::overflow_error<stdexcept>Arithmetic overflow
std::underflow_error<stdexcept>Arithmetic underflow
std::bad_alloc<new>Memory allocation failure (new failed)
std::bad_cast<typeinfo>Failed dynamic_cast to reference

Because all standard exceptions share a common base, you can catch them all with a single catch (const std::exception& e).

13.6 The what() Method

std::exception::what() returns a const char* describing the exception. It is declared virtual so derived classes can override it. Every standard exception class stores a message string and returns it via what(). 

#include <stdexcept>
#include <iostream>

int main() {
    try {
        throw std::out_of_range("index 42 is out of range [0, 10)");
    }
    catch (const std::exception& e) {
        std::cout << e.what() << "\n";
        // prints: index 42 is out of range [0, 10)
    }
}

13.7 Creating Custom Exception Classes

Custom exceptions let you convey domain-specific context. Inherit from std::exception (for minimal interface) or from std::runtime_error / std::logic_error (inherits string storage and what() for free). 

#include <stdexcept>
#include <string>

// Inheriting std::runtime_error is the simplest approach
class NetworkException : public std::runtime_error {
public:
    explicit NetworkException(const std::string& msg)
        : std::runtime_error(msg) {}
};

// Custom data fields — inherit std::exception manually
class DatabaseException : public std::exception {
    std::string m_msg;
    int         m_code;
public:
    DatabaseException(std::string msg, int code)
        : m_msg(std::move(msg)), m_code(code) {}

    const char* what() const noexcept override { return m_msg.c_str(); }
    int         code() const noexcept          { return m_code; }
};

13.8 Exception Safety Levels

Dave Abrahams defined four levels of exception safety guarantees for any operation:

LevelGuarantee
No-throw (nothrow)The operation never throws. Marked noexcept. Required for destructors, move operations, and swap.
StrongEither the operation succeeds completely, or the program state is left exactly as it was before (commit-or-rollback). Ideal but not always achievable.
BasicIf an exception is thrown, no resources are leaked and all invariants are preserved — but the exact state may change. The minimum acceptable guarantee.
NoneNo guarantee: program may be in an inconsistent state after a throw. Avoid.

13.9 Stack Unwinding

When a throw occurs, the C++ runtime searches up the call stack for a matching catch handler. As it unwinds each stack frame it destroys all local objects constructed in that frame, calling their destructors in reverse order of construction. This is called stack unwinding. 

struct Guard {
    std::string name;
    Guard(std::string n) : name(n) { std::cout << name << " created\n"; }
    ~Guard()                       { std::cout << name << " destroyed\n"; }
};

void inner() {
    Guard g("inner-guard");
    throw std::runtime_error("boom");   // triggers unwinding
}

void outer() {
    Guard g("outer-guard");
    inner();   // exception propagates up
}

int main() {
    try { outer(); }
    catch (const std::exception& e) { std::cerr << e.what() << "\n"; }
}
// Output:
// inner-guard created
// outer-guard created
// inner-guard destroyed   ← inner frame unwound first
// outer-guard destroyed   ← then outer frame
// boom

13.10 RAII and Exceptions

RAII (Resource Acquisition Is Initialization) is the pattern of tying resource lifetime to object lifetime. Because destructors run during stack unwinding, RAII objects (e.g., std::unique_ptr, std::lock_guard, std::fstream) automatically release resources even when exceptions occur — without any explicit cleanup code in catch blocks. 

#include <fstream>
#include <stdexcept>

void processFile(const std::string& path) {
    std::ifstream file(path);        // RAII: file closed in destructor
    if (!file) throw std::runtime_error("Cannot open " + path);

    std::string line;
    while (std::getline(file, line)) {
        // process line...
        if (line == "ABORT") throw std::runtime_error("Abort signal");
    }
    // file.close() called automatically even if exception thrown above
}
Key Insight With RAII, you never need try/catch just for cleanup. try/catch is only for handling or translating exceptions — not for resource management.

13.11 Rethrowing Exceptions

A bare throw; inside a catch block rethrows the current exception, preserving its original dynamic type. This is different from throw e;, which would slice the exception to the static type of e. 

void wrapper() {
    try {
        doWork();
    }
    catch (const std::exception& e) {
        logError(e.what());   // log before propagating
        throw;                // rethrow — original type preserved
        // throw e;           // WRONG: slices to std::exception
    }
}

Exception translation — catching a low-level exception and rethrowing a higher-level one — is a common pattern for layered architectures: 

catch (const std::ios_base::failure& e) {
    throw DatabaseException("I/O error reading record", 500);
}

13.12 noexcept Specifier

noexcept annotates a function as guaranteeing it will not throw. If a noexcept function does throw, std::terminate() is called immediately — no stack unwinding. 

int safeAdd(int a, int b) noexcept {
    return a + b;   // cannot throw
}

// noexcept(expr) — conditionally noexcept
template<class T>
void swap(T& a, T& b) noexcept(noexcept(T(std::move(a)))) {
    T tmp = std::move(a);
    a     = std::move(b);
    b     = std::move(tmp);
}

Destructors are implicitly noexcept in C++11 and later. Move constructors and move assignment operators should be marked noexcept to enable optimisations in the STL (e.g., std::vector uses move instead of copy only when the move is noexcept).

13.13 std::terminate and std::set_terminate

std::terminate() is called when an exception cannot be handled:

  • An exception propagates out of main().
  • A noexcept function throws.
  • An exception is thrown during stack unwinding (double exception).

By default, std::terminate calls std::abort(). You can replace the terminate handler with std::set_terminate() to log a message before aborting: 

#include <exception>
#include <iostream>
#include <cstdlib>

void myTerminate() {
    std::cerr << "[FATAL] Unhandled exception — aborting.\n";
    std::abort();
}

int main() {
    std::set_terminate(myTerminate);
    throw 42;   // no matching catch — myTerminate is called
}

13.14 Exceptions in Constructors and Destructors

Constructors

Throwing from a constructor is the correct way to signal construction failure. The partially-constructed object's already-constructed base classes and members have their destructors called during unwinding. The destructor of the failing object itself is not called (the object was never fully constructed). 

class Connection {
    Socket m_sock;
public:
    Connection(const std::string& host) {
        m_sock.connect(host);           // may throw
        // if throw, ~Socket() is called automatically
    }
    // ~Connection() NOT called if constructor threw
};

Destructors

Never let a destructor throw. Because destructors run during stack unwinding, a throw inside a destructor while another exception is active causes std::terminate(). Mark destructors noexcept (they are implicitly so in C++11) and swallow or log any internal failures: 

~FileWriter() noexcept {
    try { flush(); }         // flush may fail
    catch (...) { /* log but do not rethrow */ }
}

13.15 When NOT to Use Exceptions

  • Real-time systems: Exception handling has non-deterministic timing due to stack unwinding and heap allocation; incompatible with hard real-time deadlines.
  • Deeply embedded / bare-metal: Many microcontroller toolchains disable C++ exception support (-fno-exceptions) to reduce code size.
  • Expected/frequent failures: Parsing user input that is often invalid, searching for an element that may not exist — here, returning std::optional or an error code is more appropriate.
  • Performance-critical hot paths: Even with zero-cost exception ABIs, the tables add binary size and can affect instruction-cache locality.

13.16 Key Takeaways

  • Use exceptions for truly exceptional, unexpected failures; use error codes for expected, frequent failures.
  • Always throw by value and catch by const reference.
  • Catch-all catch(...) is a safety net — rethrow if you cannot fully handle the error.
  • Prefer inheriting from std::runtime_error or std::logic_error for custom exceptions.
  • The four safety levels: nothrow > strong > basic > none. Target strong where possible; always provide at least basic.
  • Stack unwinding calls destructors — RAII ensures automatic, leak-free resource cleanup.
  • Bare throw; rethrows without slicing; throw e; slices — know the difference.
  • Mark destructors and move operations noexcept.
  • Never throw from a destructor.
