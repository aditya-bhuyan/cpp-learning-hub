Chapter 12 — Memory Management

Deep dive into stack vs heap, manual allocation, RAII, and modern smart pointers.

📖 Learning 💻 Examples ✏️ Exercises ✅ Solutions 🧠 Quiz

12.1 Stack vs Heap Memory

In C++, programs execute inside a virtual address space partitioned into distinct memory segments. The two primary regions where runtime variables live are the Stack and the Heap (also called the free store). Understanding their operational differences is fundamental to writing safe, high-performance software.

Attribute Stack Memory Heap Memory (Free Store)
Management Automatic (compiler-managed via stack pointer) Manual (programmer or smart pointer managed)
Lifetime Tied to scope (enclosing block { ... }) Dynamic (until explicitly freed with delete)
Allocation Speed Extremely fast (single CPU instruction adjusting SP) Slower (runtime allocator searches free lists/bins)
Size Limit Small & fixed (typically 1–8 MB per thread) Large (bounded only by system RAM and virtual swap)
Fragmentation None (strictly LIFO order) Possible over time due to random allocation/freeing
Failure Mode Stack Overflow (e.g. infinite recursion) std::bad_alloc exception (out of memory) 
void stackExample() {
    int x = 42;             // Stack allocated
    double buffer[100];     // Stack allocated (800 bytes)
}                           // x and buffer automatically popped and destroyed here

void heapExample() {
    int* p = new int(42);   // Heap allocated: 'p' (stack pointer) points to heap memory
    // ...
    delete p;               // Must be explicitly freed, otherwise leaked!
}
Default Rule of Thumb Always prefer stack allocation whenever the object's lifetime matches the local scope and its size is known and moderate. Allocate on the heap only when you need dynamic lifetime (outliving the scope that created it), runtime-variable sizing, polymorphism via base pointers, or very large data buffers.

12.2 Manual Allocation: new and delete

C++ provides the new and delete operators for allocating and releasing individual objects on the heap. Unlike C's malloc() and free(), which only allocate raw uninitialized bytes, C++ operators understand object lifecycles:

  • new Type(args): Allocates memory for sizeof(Type) and invokes the constructor with the given arguments. Returns a typed pointer Type*.
  • delete ptr: Invokes the destructor of the object pointed to by ptr, then returns the allocated memory back to the heap allocator.
#include <iostream>
#include <string>
using namespace std;

class Player {
    string name_;
    int score_;
public:
    Player(const string& name, int score) : name_(name), score_(score) {
        cout << "Constructor: Player " << name_ << " created\n";
    }
    ~Player() {
        cout << "Destructor: Player " << name_ << " destroyed\n";
    }
    void print() const { cout << name_ << " has " << score_ << " points\n"; }
};

int main() {
    // Allocate single object on heap
    Player* p = new Player("Alice", 100);   // Calls Player::Player
    p->print();

    // Free allocated memory
    delete p;                               // Calls Player::~Player, then frees memory
    p = nullptr;                            // Good practice: clear dangling pointer

    return 0;
}
Never Mix C and C++ Allocation Functions Never use free() on a pointer obtained with new (the destructor will not run!), and never use delete on a pointer obtained with malloc(). Always pair new with delete, and malloc with free.

12.3 Dynamically Allocated Arrays: new[] and delete[]

When allocating contiguous arrays of dynamic size, C++ uses array forms: new[] and delete[].

  • new Type[count]: Allocates memory for count objects and default-constructs each one in order.
  • delete[] ptr: Invokes the destructor for each element in reverse order and deallocates the array block.
int size = 5;
int* arr = new int[size]{ 10, 20, 30, 40, 50 };   // C++11 list initialization

for (int i = 0; i < size; ++i) {
    cout << arr[i] << " ";
}
cout << "\n";

delete[] arr;    // MUST use delete[], NOT delete!
arr = nullptr;
The Mismatched delete Trap When you call new[], the compiler stores extra metadata (often called the array cookie) containing the number of elements so that delete[] knows how many destructors to call. If you call scalar delete arr; instead of delete[] arr;, the program exhibits undefined behavior — destructors are skipped and heap memory metadata is corrupted.

12.4 Memory Leaks and Detection

A memory leak occurs when heap-allocated memory is no longer referenced by any pointer in the program but has not been returned to the system with delete. In long-running software (servers, game engines, UI applications), leaking even small amounts per second will steadily consume system RAM, degrade performance, and ultimately crash the operating system or application. 

void leakedFunction() {
    int* leak = new int(100);
    if (someCondition()) {
        return;     // BUG: 'leak' goes out of scope, heap int(100) is orphaned forever!
    }
    delete leak;
}

Detection Tools

  1. AddressSanitizer (ASan): Built into modern GCC and Clang. Compiles lightweight instrumentation into your binary with near-zero friction:
    g++ -std=c++17 -fsanitize=address -g -O1 -o program program.cpp
    When run, ASan instantly flags memory leaks, heap buffer overflows, and use-after-free bugs with exact file and line numbers.
  2. Valgrind (Memcheck): Powerful dynamic binary instrumentation tool for Linux/macOS:
    valgrind --leak-check=full --show-leak-kinds=all ./program

12.5 Dangling Pointers and Double Delete

Manual pointer arithmetic and lifecycle management introduce two severe memory safety hazards:

  • Dangling Pointer: A pointer that points to a memory address that has already been deallocated. Dereferencing or modifying a dangling pointer is Use-After-Free (UAF) undefined behavior.
  • Double Delete: Calling delete twice on the same heap address. This corrupts internal allocator tables and crashes the application or introduces security vulnerabilities. 
int* p1 = new int(50);
delete p1;          // Memory returned to OS/allocator; p1 now dangles!

// *p1 = 100;       // UNDEFINED BEHAVIOR: writing to deallocated memory (Use-After-Free)
// delete p1;       // UNDEFINED BEHAVIOR: double delete!

p1 = nullptr;       // Safe practice: null out freed pointers
delete p1;          // SAFE: 'delete nullptr' is a well-defined no-op in C++!
Deleting nullptr is Always Safe According to the C++ standard, delete nullptr and delete[] nullptr are guaranteed to be safe and do nothing. You never need to write if (p != nullptr) delete p;.

12.6 The RAII Principle: Resource Acquisition Is Initialization

RAII (Resource Acquisition Is Initialization) is the foundational design pattern of modern C++. It states: bind the lifecycle of any resource (heap memory, file descriptors, network sockets, mutex locks) to the lifetime of a stack-allocated object.

  1. Acquire resource in constructor: When the wrapper object is created on the stack, it claims ownership of the resource.
  2. Release resource in destructor: When the wrapper object exits scope (whether normally, by return, break, or via an exception), its destructor is automatically and deterministically invoked by the runtime.
// Simple RAII wrapper around dynamic integer
class ScopedInt {
    int* ptr_;
public:
    explicit ScopedInt(int value) : ptr_(new int(value)) { }
    ~ScopedInt() {
        delete ptr_;    // Automatically executed upon leaving scope
    }

    // Disable copying to avoid double-free
    ScopedInt(const ScopedInt&) = delete;
    ScopedInt& operator=(const ScopedInt&) = delete;

    int get() const { return *ptr_; }
    void set(int v) { *ptr_ = v; }
};

void testRAII() {
    ScopedInt a(42);
    cout << a.get() << "\n";
    // No delete needed! Destructor runs automatically when testRAII finishes or throws.
}

12.7 Smart Pointers Overview

Instead of writing custom RAII wrappers for every dynamic object, C++11 introduced standardized smart pointer class templates in the <memory> header. Smart pointers act like regular pointers (overloading * and ->), but manage ownership semantics automatically with zero runtime overhead in the case of std::unique_ptr.

Smart Pointer Ownership Model Copyable? Movable? Primary Use Case
std::unique_ptr<T> Exclusive (single owner) No Yes Default choice for heap objects, polymorphics, factories
std::shared_ptr<T> Shared (reference counted) Yes Yes Shared ownership across multiple subsystems/threads
std::weak_ptr<T> Non-owning observer Yes Yes Breaks cycles in shared_ptr, caches, observer pattern

12.8 std::unique_ptr: Exclusive Ownership

std::unique_ptr<T> owns and manages another object through a pointer and disposes of that object when the unique_ptr goes out of scope. It enforces exclusive ownership: no two unique_ptr instances can manage the same object simultaneously.

  • Copying is disabled: Copy constructor and copy assignment are = delete.
  • Move semantics enabled: Ownership can be transferred explicitly using std::move().
  • Creation: Always use std::make_unique<T>() (C++14) rather than raw new.
#include <iostream>
#include <memory>
#include <string>
using namespace std;

struct Task {
    string title;
    Task(string t) : title(t) { cout << "Task '" << title << "' created\n"; }
    ~Task() { cout << "Task '" << title << "' destroyed\n"; }
    void run() const { cout << "Running " << title << "\n"; }
};

int main() {
    // 1. Creation with std::make_unique (Exception safe, clean syntax)
    auto p1 = make_unique<Task>("Compile Code");
    p1->run();

    // 2. auto p2 = p1;         // COMPILE ERROR: unique_ptr cannot be copied!

    // 3. Transfer ownership with std::move
    unique_ptr<Task> p2 = move(p1);
    // Now p1 is nullptr, p2 owns the Task

    if (!p1) {
        cout << "p1 is now empty (nullptr)\n";
    }
    p2->run();

    // 4. Member methods
    Task* raw = p2.get();       // Non-owning inspection of raw pointer
    raw->run();

    p2.reset(new Task("New Task")); // Destroys previous Task, acquires new one
    p2.reset();                     // Explicitly destroys task and resets to nullptr

    return 0;
}

std::unique_ptr with Arrays

std::unique_ptr<T[]> provides a specialization for dynamically allocated arrays that automatically calls delete[] on destruction and provides operator[]: 

auto buf = make_unique<int[]>(100);   // Allocates array of 100 ints
buf[0] = 10;
buf[99] = 20;
// Automatically freed via delete[] when 'buf' leaves scope!

12.9 std::shared_ptr: Shared Ownership & Reference Counting

std::shared_ptr<T> retains shared ownership of an object through a pointer. Multiple shared_ptr objects may own the same resource. The resource is maintained by an internal control block containing:

  • A strong reference counter: Incremented whenever a shared_ptr is copied; decremented whenever a shared_ptr is destroyed or reassigned.
  • A weak reference counter: Tracks how many std::weak_ptr instances observe the control block.
  • The custom deleter and allocator (if specified).

When the strong reference count reaches 0, the managed object is destroyed. When both strong and weak counts reach 0, the control block itself is deallocated. 

#include <iostream>
#include <memory>
using namespace std;

struct Node {
    int id;
    Node(int i) : id(i) { cout << "Node " << id << " created\n"; }
    ~Node() { cout << "Node " << id << " destroyed\n"; }
};

int main() {
    // make_shared allocates the object and control block in ONE contiguous heap chunk
    shared_ptr<Node> sp1 = make_shared<Node>(101);
    cout << "use_count: " << sp1.use_count() << "\n";  // 1

    {
        shared_ptr<Node> sp2 = sp1;  // Copying increases reference count
        cout << "use_count inside block: " << sp1.use_count() << "\n";  // 2
        cout << "sp2 id: " << sp2->id << "\n";
    } // sp2 destroyed; reference count decremented to 1

    cout << "use_count after block: " << sp1.use_count() << "\n";   // 1
    sp1.reset(); // Reference count drops to 0 -> Node 101 destroyed immediately
    cout << "sp1 reset complete\n";

    return 0;
}
Why std::make_shared is Faster Calling shared_ptr<T>(new T) performs two separate heap allocations: one for T and one for the internal control block. std::make_shared<T>() performs a single unified allocation for both, improving cache locality and performance.

12.10 std::weak_ptr: Non-Owning Observer

std::weak_ptr<T> is a smart pointer that holds a non-owning ("weak") reference to an object managed by std::shared_ptr. It must be converted to std::shared_ptr to access the referenced object.

  • Does not contribute to the strong reference count (does not prevent object destruction).
  • expired(): Returns true if the managed object has already been destroyed.
  • lock(): Safely converts the weak reference into a temporary std::shared_ptr. Returns nullptr if the object no longer exists.
shared_ptr<int> sp = make_shared<int>(42);
weak_ptr<int> wp = sp;   // wp observes sp, use_count stays 1

cout << "use_count: " << sp.use_count() << "\n";   // 1
cout << "expired? " << boolalpha << wp.expired() << "\n"; // false

// To access the value, convert to shared_ptr via lock():
if (auto locked = wp.lock()) {
    cout << "Locked value: " << *locked << "\n";
}

sp.reset(); // Object destroyed!

if (auto locked = wp.lock()) {
    // Will not execute
} else {
    cout << "Object has been destroyed, lock returned nullptr\n";
}

12.11 The Circular Reference Problem and Weak Pointers

When two objects hold std::shared_ptr references to each other, a cyclic dependency (circular reference) is formed. Even when all external pointers go out of scope, each object's use_count remains at 1 because the other object holds a reference. Consequently, neither destructor is ever executed, causing a silent memory leak. 

// THE BUG: Circular reference
struct B; // Forward declaration

struct A {
    shared_ptr<B> b_ptr;
    ~A() { cout << "~A destroyed\n"; }
};

struct B {
    shared_ptr<A> a_ptr;   // Cycle!
    ~B() { cout << "~B destroyed\n"; }
};

void createCycle() {
    auto a = make_shared<A>();
    auto b = make_shared<B>();
    a->b_ptr = b;
    b->a_ptr = a;
} // 'a' and 'b' exit scope, but use_count for both is 1 -> NEITHER DESTRUCTOR RUNS!

The Fix: Break the Cycle with std::weak_ptr

Change one of the links (e.g. child-to-parent or back-pointer) to std::weak_ptr:

struct BFixed {
    weak_ptr<A> a_ptr;    // Weak link breaks the ownership cycle!
    ~BFixed() { cout << "~BFixed destroyed\n"; }
};

12.12 Custom Deleters

By default, smart pointers invoke delete on their managed pointer. However, you can provide a custom deleter to clean up legacy C APIs (e.g. fclose for FILE*, free() for C allocations, or custom OS handles).

Custom Deleter in std::unique_ptr

For unique_ptr, the deleter type is part of the template signature:

#include <cstdio>
#include <memory>

struct FileCloser {
    void operator()(FILE* fp) const {
        if (fp) {
            cout << "Closing file via custom deleter\n";
            fclose(fp);
        }
    }
};

void fileExample() {
    // unique_ptr<Type, DeleterType>
    unique_ptr<FILE, FileCloser> file(fopen("test.txt", "w"));
    if (file) {
        fputs("Hello RAII\n", file.get());
    }
    // fclose(file.get()) called automatically upon leaving scope!
}

Custom Deleter in std::shared_ptr

For shared_ptr, the deleter is passed as a constructor argument (type erasure), keeping shared_ptr<FILE> signature clean:

void sharedFileExample() {
    // Pass lambda or function pointer as constructor argument
    shared_ptr<FILE> file(fopen("log.txt", "w"), [](FILE* fp) {
        if (fp) {
            cout << "Closing log file\n";
            fclose(fp);
        }
    });
}

12.13 std::unique_ptr as a Factory Return Type

In modern polymorphic designs, factory functions should return std::unique_ptr<Base>. This provides the caller with the maximum flexibility:

  • The caller receives exclusive, zero-overhead ownership.
  • If the caller needs shared ownership, std::unique_ptr implicitly converts to std::shared_ptr via std::move.
class Shape {
public:
    virtual void draw() const = 0;
    virtual ~Shape() = default;   // Always virtual destructor for base!
};

class Circle : public Shape {
public:
    void draw() const override { cout << "Drawing Circle\n"; }
};

class Square : public Shape {
public:
    void draw() const override { cout << "Drawing Square\n"; }
};

// Factory function
unique_ptr<Shape> createShape(const string& type) {
    if (type == "circle") return make_unique<Circle>();
    if (type == "square") return make_unique<Square>();
    return nullptr;
}

int main() {
    auto shape1 = createShape("circle");
    shape1->draw();

    // Smoothly convert to shared_ptr if needed
    shared_ptr<Shape> sharedShape = createShape("square");
    sharedShape->draw();

    return 0;
}

12.14 When to Use Raw Pointers vs Smart Pointers

The C++ Core Guidelines established clear conventions for pointer usage in modern C++:

Pointer / Reference Type Intent & Ownership Guidelines
std::unique_ptr<T> Sole owner of dynamic object Default choice for managing heap lifetime. Pass by value to sink/transfer ownership.
std::shared_ptr<T> Shared owner of dynamic object Use only when multiple independent owners genuinely share lifetime.
std::weak_ptr<T> Non-owning observer of shared resource Use for caches, observer pattern, and breaking cycles.
T& (Reference) Non-owning observer (guaranteed non-null) Preferred parameter type for functions that need to inspect or mutate an object without taking ownership.
T* (Raw Pointer) Non-owning observer (optional / nullable) Use for parameter passing when nullptr is a valid argument. Never use raw pointers to express ownership or call delete!

12.15 Memory Alignment and Placement New

For high-performance systems and embedded programming, C++ allows direct control over memory layout:

  • alignof(Type): Queries the alignment requirement (in bytes) of a type.
  • alignas(N): Forces custom byte alignment for structs or variables.
  • Placement New: Constructs an object in a pre-allocated memory buffer without performing heap allocation. Requires #include <new>. Because placement new did not allocate heap memory, you must not call delete; instead, manually invoke the destructor: ptr->~Type(). 
#include <iostream>
#include <new>   // Required for placement new
using namespace std;

struct Item {
    int id;
    Item(int i) : id(i) { cout << "Item " << id << " constructed in buffer\n"; }
    ~Item() { cout << "Item " << id << " explicitly destroyed\n"; }
};

int main() {
    // Pre-allocated stack memory buffer
    alignas(Item) char buffer[sizeof(Item)];

    // Placement new: construct Item inside 'buffer'
    Item* itemPtr = new (buffer) Item(99);

    cout << "Item id: " << itemPtr->id << "\n";

    // Clean up: Manually invoke destructor!
    itemPtr->~Item();

    return 0;
}

12.16 Key Takeaways

  • The Stack is fast, automatic, and scope-bound; the Heap is dynamic, manual, and sized for large allocations.
  • Every new must be paired with delete, and every new[] must be paired with delete[]. Mixing them causes undefined behavior.
  • RAII ties resource management to object lifetimes via stack destructors, guaranteeing cleanup even during exceptions.
  • Use std::unique_ptr for exclusive ownership (zero overhead, move-only). Create with std::make_unique.
  • Use std::shared_ptr for shared ownership (reference counted). Create with std::make_shared.
  • Use std::weak_ptr to break circular references and safely observe shared_ptr instances without extending their lifetime.
  • Raw pointers and references are for non-owning observation; smart pointers are for ownership and lifetime management.
